# 프론트 API 연결과 실제 서버 확인

후속 변경: [대상자 등록·수정 화면](participant-management.md)이 추가되었다. 아래 등록·수정 미포함 설명은 최초 API 연결 PR의 범위를 기록한 것이다.

2026-11-18 · `feature/frontend-api-integration`

기준 main은 PR #7 병합 커밋 `63f43390220335647477eb8884e08dd904e2e304`이다.

## 구현

메인 화면에서 서버 주소 입력 → 로그인 → 서버 대상자 선택 → 기존 영상 처리 및 좌표 준비 → 실제 서버 저장 → 기록 및 결과 조회로 진행한다.
대상자 UUID는 서버 목록에서 가져오며 촬영 당시 키는 별도 입력한다. 대상자 생성·수정 화면은 이번 범위에 포함하지 않는다.
등록된 대상자가 없거나 생년월일이 없으면 담당자에게 테스트 대상자 등록·수정을 요청한다.

`ApiClient`는 로그인(form), 대상자 목록, 측정 저장, 페이지당 20개 기록 조회, 결과 조회를 담당한다.
원본 영상·비밀번호·파일 경로를 측정 요청에 넣지 않는다. 비밀번호는 로그인 요청에만 사용하고 토큰은 메모리에만 둔다.
외부 서버는 HTTPS를 사용하고 HTTP는 localhost/127.0.0.1/IPv6 loopback에서만 허용한다.
리다이렉트는 거절하며 요청 시간 제한은 30초다. 네트워크 실패 시 자동으로 새 저장 요청을 만들지 않는다.
메인 HTML의 connect-src 정책도 HTTPS와 로컬 개발 HTTP API 연결을 허용한다. 서버 주소가 확정되면 배포용 CSP를 해당 origin으로 좁히는 것이 후속 작업이다. 개발 전용 dev.html은 기존 self 정책을 유지한다.

좌표를 준비할 때 생성한 키와 직렬화한 본문을 저장 재시도에 그대로 사용한다.
201 최초 저장과 200 재전송 응답 모두 대상자·측정 ID를 확인한 뒤 완료로 표시한다.
401이면 상단에서 같은 계정으로 인증을 갱신하고 기존 저장 버튼으로 재시도한다.
로그인 이후 서버 주소와 계정은 잠가 다른 서버·사용자로 재전송되지 않게 한다.
409 REQUEST_IN_PROGRESS는 Retry-After만큼 기다리며, 충돌이나 422 오류는 해당 요청의 저장 버튼을 막는다.
처리 결과가 없는 경우 점수 0이나 분석 진행 중으로 표시하지 않는다.

## 실행

저장소 루트에서 `npm run dev:mobile`을 실행하고 표시된 주소로 접속한다.
메인 화면에 실제 테스트 서버 주소를 입력한다. 기본 주소가 필요하면 `mobile/.env.local`에
`VITE_API_BASE_URL=https://실제-테스트-서버`를 설정하고 Vite를 재시작한다.
VITE 변수는 브라우저에 공개되므로 비밀번호·토큰을 넣지 않는다. `.env.local`은 커밋하지 않는다.

기존 서버 없는 영상 개발 화면은 `/dev.html`에서 사용할 수 있다. 모의 저장은 실제 DB 저장이 아니다.

백엔드에는 PR #7 코드와 `alembic upgrade head`가 적용되어야 한다.
CORS_ALLOW_ORIGINS에는 브라우저 주소를 정확히 넣는다 (예: `http://localhost:5173`).
`http://127.0.0.1:5173`은 다른 origin이다. 갤럭시의 localhost는 PC가 아닌 휴대폰 자신이다.
휴대폰 테스트는 팀원이 제공한 HTTPS 테스트 서버를 사용하며 인증서 검증을 끄지 않는다.

## 검증 결과와 남은 확인

- 로컬 테스트: 기존 123개 + HTTP 어댑터 10개 = 133개 통과.
- 계약 및 모바일 TypeScript 검사, 모바일 production 빌드 통과.
- Frontend CI를 추가했다. PR에서 계약 테스트와 모바일 빌드를 실행한다.
- HTTP 어댑터 테스트는 주입한 가짜 transport를 사용한다. 실제 백엔드 접속 테스트가 아니다.
- 브라우저 미리보기 도구의 세션 오류로 화면 조작·모바일 실기기 검증은 수행하지 못했다.

서버 접속 정보 준비 후 합성 대상자와 동의받은 테스트 영상으로 다음을 확인한다.

1. 잘못된 비밀번호 오류, 정상 로그인, 대상자 목록 표시.
2. 대상자 선택 → 영상 추출 → JSON 준비 → 서버 저장 성공 및 기록 1건 확인.
3. 응답 유실·취소 후 같은 버튼으로 재시도해 기록이 늘어나지 않는지 확인.
4. 인증 만료 후 같은 계정으로 갱신하고 같은 요청으로 재시도.
5. 기록 페이지 이동·상세 조회, 결과 없음 표시, 값이 null인 지표 표시.
6. 대상자 전환·로그아웃에서 이전 요청의 늦은 응답이 새 화면에 나타나지 않는지 확인.

새로고침·로그아웃·대상자 전환·입력 변경·영상 재추출은 메모리의 준비된 요청을 없앨 수 있다.
저장 응답이 불명확하면 먼저 같은 요청으로 재시도하거나 서버 기록을 확인한다.
브라우저 종료 후에도 재시도 요청을 복구하는 기능과 자동 GDI 실행은 별도 범위다.

PM이 PR과 Frontend CI/Backend CI 결과를 확인한 뒤 병합한다. 테스트 서버 배포와 실제 흐름 검증까지 끝나야 통합 완료로 판단한다.
